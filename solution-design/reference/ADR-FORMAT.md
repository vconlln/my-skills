# 架构决策记录（ADR）格式

ADR 记录「当时为什么这么决定」。代码只能表达决定的结果，表达不了被否掉的备选和背后的约束——ADR 补的就是这一块。

## 存放与命名

- 目录：`docs/adr/`，**懒创建**——第一个 ADR 需要时才建
- 命名：`NNNN-短标题.md`，四位递增编号（如 `0001-写模型选用postgres.md`）
- 写之前扫一遍目录，取现有最大号 +1

## 模板（刻意保持极简）

```markdown
# {决策标题}

{背景与约束，一两句}{决定，一句}{核心理由，一句}
```

一段话就够。ADR 的价值在于「记了」和「为什么」，不在篇幅。

## 可选小节（默认都不加）

| 小节 | 什么时候才加 |
|------|-------------|
| 状态：草案 / 已接受 / 已废弃 / 已被 NNNN 取代 | 该决定日后会被重新讨论时 |
| 备选与放弃理由 | 放弃的理由不显而易见时 |
| 影响 | 存在非显然的连带后果时 |

## 值不值得记：三问判定

全答「是」才写，否则不记：

1. **反悔贵吗？** ——改主意成本可忽略的，不记，回头改掉就是
2. **后人会困惑吗？** ——看代码就能猜到缘由的，不记
3. **有真备选吗？** ——当时只有一条路可走的，不记，那只是做了显然的事

## 典型该记的决策

- **架构骨架**：单体还是拆分、读写是否分离、是否事件溯源
- **领域间通信**：事件驱动还是同步调用
- **重锁定选型**：数据库、消息中间件、认证方案、部署平台——换一次伤筋动骨的才记，随手可替换的库不记
- **数据归属边界**：「订单数据只归订单域，别处仅存 ID」——「不允许什么」和「允许什么」同样值得记
- **明知故犯的例外**：如刻意不用 ORM 而手写 SQL——不记下来，下一个人会把它当 bug「修掉」
- **外部强约束**：合规禁用、合作方 SLA、性能硬指标——这些在代码里完全看不见
- **费解的放弃**：弃 A 选 B 的理由说不清时，六个月后必有人再提议 A，先记下来省得重吵

## 与技能流程的配合

Step 4 的每个《决策记录》条目过一遍三问判定，全中即按本格式即时写入 `docs/adr/`；不满足的留在方案文档的决策记录表里即可。
