# ADR 格式（架构决策记录）

ADR 存放于 `docs/adr/`，顺序编号：`0001-slug.md`、`0002-slug.md`……目录**懒创建**：第一个 ADR 需要时才建。

## 模板

```markdown
# {决策的简短标题}

{1~3 句话：背景是什么、决定了什么、为什么。}
```

就这些。ADR 可以只有一个段落——价值在于记录**做过这个决定**和**为什么**，不在于填满小节。

## 可选小节（仅在真有增量价值时加，多数 ADR 用不上）

- **状态**（frontmatter：`proposed | accepted | deprecated | superseded by ADR-NNNN`）：决定会被重新讨论时有用
- **考虑过的备选**：被否决的备选值得记住时
- **后果**：非显而易见的下游影响需要点名时

## 编号

扫描 `docs/adr/` 取现有最大号 +1。

## 何时值得写（三条全中才算）

1. **难以逆转**：事后改主意的代价可观
2. **无上下文会费解**：未来的读者看到代码会问「当时为什么这么做？」
3. **真实权衡的产物**：存在真正的备选，且因具体理由选了这个

易逆转 → 跳过（回头改掉就是了）；不令人费解 → 没人会问为什么；没有真实备选 → 除了「做了显然的事」没什么可记。

## 什么算合格（示例清单）

- **架构形态**：「用 monorepo」「写模型事件溯源，读模型投影到 Postgres」
- **上下文间集成模式**：「订单与计费通过领域事件通信，不用同步 HTTP」
- **带锁定的技术选型**：数据库、消息总线、认证提供方、部署目标——不是每个库都记，只记换掉要花一个季度的那种
- **边界与归属决定**：「客户数据归客户上下文所有，其他上下文仅按 ID 引用」——明确的「不」和「是」同样有价值
- **刻意偏离显然路径**：「因 X 用手写 SQL 不用 ORM」——防止下个工程师把故意为之当 bug「修掉」
- **代码里看不见的约束**：「因合规要求不能用某云」「因合作方契约要求响应 <200ms」
- **非显而易见的否决**：因微妙理由弃 GraphQL 选 REST 要记下来，否则六个月后有人会再提 GraphQL
