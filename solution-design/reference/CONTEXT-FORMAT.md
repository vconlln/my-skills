# 术语表格式（CONTEXT.md）

领域术语的落盘格式。术语在质询中敲定的那一刻写入，不攒批。

## 结构

```markdown
# {上下文名称}

{一两句话说明这个上下文是什么、为什么存在。}

## 领域词汇

**订单**：
{术语的一两句定义}
_避免使用_：采购、交易

**发票**：
交付后向客户发出的付款请求。
_避免使用_：账单、付款申请

**客户**：
下单的个人或组织。
_避免使用_：客户端、买家、账户
```

## 规则

- **有主见**：同一概念有多个说法时，选定最佳的一个，其余列入 `_避免使用_`
- **定义紧凑**：最多一两句；定义它**是什么**，不定义它做什么
- **只收本上下文特有的术语**：通用编程概念（超时、错误类型、工具模式）即使项目大量使用也不收。加词前先问：这是本领域独有的概念，还是通用编程概念？只有前者收
- **自然分组**：术语形成自然聚类时用子标题归类；单一领域平铺即可
- **纯词汇表**：不写实现细节、不写方案、不当草稿纸

## 单上下文 vs 多上下文仓库

- **单上下文（多数仓库）**：仓库根放一个 `CONTEXT.md`
- **多上下文**：仓库根放 `CONTEXT-MAP.md`，列出各上下文的位置与关系：

```markdown
# 上下文映射

## 上下文

- [订单](./src/ordering/CONTEXT.md)：接收并跟踪客户订单
- [计费](./src/billing/CONTEXT.md)：生成发票并处理付款

## 关系

- **订单 → 计费**：订单发出 `OrderPlaced` 事件；计费消费它生成发票
- **订单 ↔ 计费**：共享 `CustomerId` 与 `Money` 类型
```

判定规则：

| 仓库现状 | 处理方式 |
|----------|---------|
| 根有 `CONTEXT-MAP.md` | 读它定位各上下文，判断当前话题属于哪个 |
| 只有根 `CONTEXT.md` | 单上下文 |
| 都没有 | 首个术语敲定时**懒创建**根 `CONTEXT.md` |

多上下文时若判断不了当前话题归属哪个上下文，直接问用户。
