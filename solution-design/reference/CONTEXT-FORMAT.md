# 领域词汇表格式（CONTEXT.md）

同一个词，不同人理解不同，是方案讨论里最贵的隐性成本。`CONTEXT.md` 是项目的领域词汇表：每个术语一个权威定义，全项目只此一份。

## 条目格式

```markdown
**术语**：
定义：一两句话，说「它是什么」，不说它做什么。
避免：<常见误用词，逗号分隔>
```

示例（内容平台领域）：

```markdown
**专栏**：
定义：作者署名下的内容容器，由若干篇稿件组成。
避免：栏目、频道、合集

**稿件**：
定义：作者提交的待发布内容单元，一篇稿件只属于一个专栏。
避免：文章、内容、post

**审稿单**：
定义：编辑对一篇稿件的一次完整审核记录，含结论与批注。
避免：审核、工单
```

## 编写规则

- **一词一义**：同一概念有多个说法时，选定一个，其余进「避免」列
- **定义紧凑**：最多两句；定义「是什么」，不定义「做什么」
- **只收领域词**：本项目领域特有的概念才收；通用技术词（超时、重试、缓存、分页）即使高频使用也不收
- **不写实现**：不写技术方案、不写接口签名、不当草稿纸——它是词汇表，不是设计文档
- **自然分组**：术语多且成簇时加子标题归类，少则平铺

## 放在哪里

| 项目形态 | 放置方式 |
|----------|---------|
| 单领域（多数项目） | 仓库根一个 `CONTEXT.md` |
| 多领域 | 仓库根 `CONTEXT-MAP.md` 做索引，各领域词汇表放各领域目录内 |

多领域时 `CONTEXT-MAP.md` 用表格做路由：

```markdown
# 领域映射

| 领域 | 词汇表 | 职责 |
|------|--------|------|
| 内容 | src/content/CONTEXT.md | 稿件与专栏的生命周期 |
| 审核 | src/review/CONTEXT.md | 审稿流程与结论 |
```

领域之间的事件流向与依赖，写在各自 `CONTEXT.md` 末尾的「与其他领域的关系」小节。

判定与创建规则：

- 有 `CONTEXT-MAP.md` → 多领域：当前话题先定位领域再读写词汇表
- 只有根 `CONTEXT.md` → 单领域
- 都没有 → **懒创建**：第一个术语敲定时创建根 `CONTEXT.md`
- 拿不准当前话题归属哪个领域 → 直接问用户

## 与技能流程的配合

- Step 2 摸底：通读既有词汇表，作为《现状摸底》的领域词汇清单
- Step 3 质询：术语敲定的那一刻即时写入，不攒批
- Step 6 收尾：只核对完整性，不重写
