# 场景驱动的方案设计（solution-design）

```
场景定调 → 现状摸底 → 质询识别需求 → 升级/新开发判定 → 方案设计 → 确认落盘
```

三条铁律：

1. **事实自己查，决策问用户** —— 代码和文档能回答的（现有能力、旧方案内容、接口签名）派子代理去查，绝不拿去问用户；只把「要什么、选哪个」的决策交给用户
2. **需求与术语，不落盘不算敲定** —— 每条需求在被用户确认的那一刻，立即按 [REQUIREMENT-TEMPLATE.md](reference/REQUIREMENT-TEMPLATE.md) 写入《需求清单》；每个领域术语敲定的那一刻，立即按 [CONTEXT-FORMAT.md](reference/CONTEXT-FORMAT.md) 写入项目 `CONTEXT.md`，都不攒到最后
3. **不默认重写** —— 升级/新开发必须按 Step 4 判定表给出依据；默认倾向最小改动半径

## 使用时机

- 有旧代码/旧方案背景，要设计升级方案或新开发方案
- 用户给出使用场景，希望「参考过去的方案」做设计
- 需求还很模糊，需要质询式访谈逐条敲定并沉淀为结构化需求清单

## 与其他技能的关系

- **上游**：dev-workflow「需求理解」的产出可直接作为 Step 1 输入（非必须）
- **历史方案来源**：[PAST-SOLUTIONS.md](reference/PAST-SOLUTIONS.md)（用户维护的索引）+ 自动扫描 `docs/**/方案设计.md`、`docs/**/需求理解.md`（dev-workflow 落盘的历史），两者合并
- **下游**：spec-driven-coding（按规范与公共库编码）或 dev-workflow「代码实现」

## 任务进度

开始前复制此清单，逐步勾选：

```
任务进度：
- [ ] Step 1：场景定调
- [ ] Step 2：现状摸底（旧方案 + 现有代码）
- [ ] Step 3：质询式需求识别
- [ ] Step 4：升级 vs 新开发判定
- [ ] Step 5：设计方案
- [ ] Step 6：确认与落盘
```

## Step 1：场景定调

1. 使用场景三问：**谁**、**在什么情况下**、**要解决什么问题**
2. 形成初步方向假设（升级 or 新开发）——仅用于导航 Step 2 的摸底范围，Step 4 才正式判定
3. 输出《场景卡》（格式见 REQUIREMENT-TEMPLATE.md 的清单头）

## Step 2：现状摸底（查事实，不问用户）

1. **找过去的方案**：
   - 读 [PAST-SOLUTIONS.md](reference/PAST-SOLUTIONS.md) 索引（若含「待填充」标记则跳过并提醒用户维护，以自动扫描为准）
   - 扫描 `docs/**/方案设计.md` 与 `docs/**/需求理解.md`，时间标题即历史版本，定位与本次场景相关的条目
2. **摸现有代码**：派子代理阅读相关模块——架构与模块边界、公共接口、与本次场景相关的既有能力、明显技术债
3. **读领域词汇**：若项目根存在 `CONTEXT.md`（或 `CONTEXT-MAP.md` 指向多个上下文），通读作为既有术语来源；用户用词与之冲突时在 Step 3 当场质询
4. 产出《现状摸底》四张清单：现有能力 / 相关历史方案（含状态）/ 硬约束 / 既有领域词汇

## Step 3：质询式需求识别

把需求点组织成**决策树**，按**轮次**质询：

1. 每轮只问**前沿**：所有前提已明确、现在就能问的问题；一次编号列出，每题附**推荐答案**，然后等待用户回答
2. 用户的回答重塑决策树：已敲定的解锁下游问题；依赖本轮未决问题的，留给后面的轮次
3. **事实类问题不进轮次，且不阻塞**：代码/文档能查的（旧方案怎么做的、现有接口长什么样）派子代理去查，查到后作为已定前提；在查的事实视为未定前提——只有依赖它的问题等待，其余前沿问题照常发问
4. **即时落盘**：每敲定一条需求，立即按 [REQUIREMENT-TEMPLATE.md](reference/REQUIREMENT-TEMPLATE.md) 写入《需求清单》
5. **术语纪律**：用户用到模糊或一词多义的术语时，提出精确的规范术语（「你说的『账户』是指客户还是用户？这是两个概念」）；术语与既有 `CONTEXT.md` 或代码用法冲突时当场质询（「代码里 X 指的是 A，你刚说的像 B，哪个对？」）；需求之间的关系用具体边界场景压测（构造极端/边缘场景，逼出概念边界的精确表述）。术语敲定即写入项目 `CONTEXT.md`（格式见 [CONTEXT-FORMAT.md](reference/CONTEXT-FORMAT.md)，懒创建）
6. 用户答「不知道」→ 记为「待定」状态，视为需要原型或调研的信号，不硬猜
7. 结束条件：前沿为空——每个需求点都被确认或被显式排除，无静默假设

轮次提问格式：

```
❓ **Q1** - **<问题标题>**：<问题正文，可含候选项>

➡️ 推荐：<你的推荐及理由>
```

## Step 4：升级 vs 新开发判定

逐行给证据（证据来自 Step 2 摸底，不凭印象）：

| 判定维度 | 升级倾向 | 新开发倾向 |
|----------|----------|------------|
| 需求与现有能力 | 同族，大部分已覆盖 | 方向性不匹配 |
| 改动半径 | 收敛在少数模块 | 波及面接近重写 |
| 旧方案健康度 | 仍在演进 | 已废弃/技术债深 |
| 成本与风险 | 升级 < 重写 | 升级 ≥ 重写 |

结论写入《决策记录》（格式见 [DESIGN-TEMPLATE.md](reference/DESIGN-TEMPLATE.md)）：决策点 / 结论 / 依据 / 放弃的备选。
仅当同时满足「难逆转 + 后人无上下文会费解 + 真实权衡取舍」三条时，按 [ADR-FORMAT.md](reference/ADR-FORMAT.md) 的模板与编号规则写入 `docs/adr/`（懒创建；什么算合格 ADR 见该文件的判定清单）。

## Step 5：设计方案

按 Step 4 结论选路径，模板见 [DESIGN-TEMPLATE.md](reference/DESIGN-TEMPLATE.md)：

- **升级路径**：以旧方案为基线的 diff 式方案——保留/修改/新增/废弃四类变更 + 兼容与迁移 + 回滚
- **新开发路径**：完整方案——选型/架构/模块/接口/数据模型/实现计划（结构与 dev-workflow 方案设计输出对齐）
- 两条路径都必须带**《需求 ↔ 方案落点》追溯表**：每条 P0/P1 需求对应方案中的落点；不承接的需求显式列出并给理由

## Step 6：确认与落盘

1. 呈现《需求清单》+《决策记录》+ 方案全文，请求用户确认共识；未确认前不得进入实现
2. 确认后按 dev-workflow 落盘规则**追加写入**：
   - `docs/<module>/需求识别.md` ←《需求清单》
   - `docs/<module>/方案设计.md` ← 方案全文（升级方案在开头注明基线方案）
   - 目录不存在则创建；文件存在则追加不覆盖；先写时间标题 `## YYYY-MM-DD HH:mm`，末尾加分隔线 `---`；无法确定模块则回退 `docs/` 根目录
   - `CONTEXT.md` 术语表与 `docs/adr/` 决策记录已在会话中**即时写入**（多上下文仓库按 `CONTEXT-MAP.md` 定位，见 [CONTEXT-FORMAT.md](reference/CONTEXT-FORMAT.md)），本步只核对完整性，不重写
3. 衔接提示：「方案已落盘，可用 spec-driven-coding 按规范编码，或 dev-workflow 代码实现」
4. 收尾回写：在技能的 [PAST-SOLUTIONS.md](reference/PAST-SOLUTIONS.md) 索引中补一行本次方案（方案名/路径/状态/核心思路），喂饱下一次「参考过去的方案」

## 注意事项

- 方案规模与需求规模匹配：三条需求的小场景不做五层架构设计
- 术语与现有代码或旧方案冲突时当场指出（「代码里 X 指的是 A，你刚说的像是 B，哪个对？」）
- 质询轮次建议控制在 3~5 轮；问出 200 个问题说明场景太大，先拆场景再回来
