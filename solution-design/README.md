# solution-design · 场景驱动的方案设计

有旧代码/旧方案背景时的深度方案设计技能：**摸底现状 → 质询敲定需求 → 判定升级或新开发 → 产出可追溯的方案**。

```
场景定调 → 现状摸底 → 质询识别需求 → 升级/新开发判定 → 方案设计 → 确认落盘
```

## 技能说明

### 使用时机

- 有旧代码、旧方案背景，要设计**升级方案**或**新开发方案**
- 用户给出使用场景，希望「参考过去的方案」做设计
- 需求模糊，需要质询式访谈逐条敲定并沉淀为结构化需求清单

> 从零开始、无旧系统背景的简单设计，直接用 dev-workflow 的「方案设计」即可，不必动用本技能。

### 六步流程

| 步骤 | 做什么 | 产出 |
|------|--------|------|
| Step 1 场景定调 | 使用场景三问（谁/何时/解决什么），形成方向假设 | 《场景卡》 |
| Step 2 现状摸底 | 派子代理查旧方案（PAST-SOLUTIONS.md + docs/ 扫描）与现有代码；读既有领域词汇 | 《现状摸底》四张清单 |
| Step 3 质询识别需求 | 决策树 + 前沿 + 轮次提问（每题附推荐答案）；术语质询与精确化；敲定即写入需求清单与 CONTEXT.md | 《需求清单》+ 术语表 |
| Step 4 升级/新开发判定 | 四维判定表逐行给证据；合格决策即时写 ADR | 《决策记录》(+ADR) |
| Step 5 设计方案 | 升级走 diff 式模板，新开发走完整模板，均带追溯表 | 方案全文 |
| Step 6 确认落盘 | 用户确认后按 dev-workflow 落盘规则追加写入 docs/ | `docs/<module>/需求识别.md` + `方案设计.md` |

### 三条铁律

1. **事实自己查，决策问用户** —— 代码/文档能回答的派子代理查，绝不问用户
2. **需求不进模板，不算敲定** —— 用户确认的瞬间即写入《需求清单》
3. **不默认重写** —— 升级/新开发必须按判定表给依据，默认倾向最小改动半径

### 核心机制

本技能完全自包含，所有机制内置，不调用、不依赖任何外部技能：

| 机制 | 落点 |
|------|------|
| 质询访谈（决策树、前沿、轮次、每题附推荐答案、事实自查决策问人、探查不阻塞） | Step 3 |
| 即时落盘（需求确认即写需求清单；术语敲定即写 CONTEXT.md） | Step 3 |
| 术语纪律（模糊术语精确化、与词汇表/代码用法冲突当场质询、边界场景压测） | Step 3 |
| 领域词汇表 CONTEXT.md（单/多领域路由、懒创建） | Step 2/3/6，[CONTEXT-FORMAT.md](reference/CONTEXT-FORMAT.md) |
| 架构决策记录 ADR（三问判定 + 编号规则，合格决策即时写入 docs/adr/） | Step 4，[ADR-FORMAT.md](reference/ADR-FORMAT.md) |

与 dev-workflow 的衔接（历史方案来源、落盘规则、上下游）见下方「与其他技能的关系」。

## 需要补充的内容

### 1. `reference/PAST-SOLUTIONS.md` —— 过去的方案索引

技能会自动扫描 `docs/**/方案设计.md`（dev-workflow 落盘的历史），但**跨仓库方案、已下线方案、核心思路摘要**只有人工索引里有。建议每完成一次方案设计回来补一行：

| 方案名 | 路径/位置 | 状态 | 核心思路（一句话） | 关键接口/模块 | 备注 |
|--------|-----------|------|--------------------|----------------|------|

状态受控三值：`在用` / `演进中` / `已废弃`（已废弃必填废弃原因）。

### 2. `reference/REQUIREMENT-TEMPLATE.md` —— 可按团队习惯微调

默认模板已可直接使用（固定字段名 + 受控值 + REQ 稳定 ID + Given-When-Then 验收）。若团队有额外必填字段（如「负责人」「迭代号」），在单条需求格式中加一行即可，**不要改动受控值**（P0/P1/P2、三种状态），那是 AI 高准确率识别的基础。

### 3. `reference/DESIGN-TEMPLATE.md` —— 可按项目类型扩展

如项目有固定架构视图（如部署图、时序图）或公司方案评审模板，往对应路径模板中加节即可；《需求 ↔ 方案落点追溯表》与《决策记录》两个尾节**不可删除**。
