# spec-driven-coding · 规范驱动编码

依据**开发规范**与**公共库**进行代码开发的流程技能。强制执行四步工作流：

```
需求分解 → 熟悉开发规范与公共库接口 → 代码实现 → shell_check 检查优化
```

## 技能说明

### 使用时机

- 要求按开发规范、公共库进行代码开发
- 给出需求，期望走「分解 → 熟悉规范 → 实现 → 检查优化」完整流程
- 提到「按规范开发」「用公共库」「规范编码」「过 shell_check」等关键词

### 工作流程

| 步骤 | 做什么 | 产出 |
|------|--------|------|
| Step 1 需求分解 | 拆解为可独立实现、可独立验证的子任务，明确输入/输出/边界/依赖 | 《需求分解清单》表格 |
| Step 2 熟悉规范与公共库 | 通读 `reference/` 下两个知识库，圈定本次涉及的规范条目与公共库接口 | 对照清单 |
| Step 3 代码实现 | 按子任务顺序实现；公共库已有的能力**必须复用，禁止重复造轮子**；逐条对照规范自查 | 实现代码 |
| Step 4 检查与优化 | 运行检查命令 → 逐条处理告警（误报需注明理由）→ 零告警后优化（去重/简化/清死代码）→ **复跑确认仍通过** | 通过检查的最终代码 |

### 两条铁律

1. **规范即准绳，公共库优先** —— 实现必须符合 `reference/STANDARDS.md`，公共库已有的能力禁止重复造轮子
2. **检查不过，不算完成** —— shell_check 通过、且优化后复跑仍通过，才能声称完成

### 空模板保护

知识库未填充时（文件含「待填充」标记），Step 2 会主动停下提醒填充；或经确认后按语言通用最佳实践降级继续，并在交付物中注明。

### 与 dev-workflow 的关系

- dev-workflow 的「需求理解 / 方案设计」产出可直接作为本技能 Step 1 的输入；本技能聚焦**编码与检查优化**阶段
- 检查通过后如需人工审查，衔接 dev-workflow 的「代码审查」步骤

## 需要补充的内容

以下三处为空模板，**填充后技能才能发挥完整约束力**：

### 1. `reference/STANDARDS.md` —— 开发规范

五个预留小节，逐条替换「待填充」标记，条目建议编号（便于实现时逐条引用自查）：

| 小节 | 填什么 | 示例 |
|------|--------|------|
| 1. 语言与框架 | 语言版本、框架、运行环境、编译选项 | 「Go 1.22，禁用 cgo」 |
| 2. 命名约定 | 文件、类型、函数、变量、常量、宏的命名规则 | 「错误变量以 `err` 结尾」 |
| 3. 目录与文件结构 | 源码/头文件/测试/脚本的目录组织 | 「测试与源文件同目录，`_test.go` 后缀」 |
| 4. 错误处理约定 | 错误码、异常、返回值检查、日志规范 | 「错误必须处理，禁止 `_ =`」 |
| 5. 编码强制约定 | 内存、并发、安全、性能、禁用写法等硬性要求 | 「禁止裸 `go func`，必须带超时」 |

### 2. `reference/COMMON-LIBRARIES.md` —— 公共库接口

按文件内注释模板**逐库添加一节**，每节包含：

- 引入方式（如 `import xxx from "..."` / `#include <xxx.h>`）
- 一句话功能说明
- 核心接口表（接口 / 签名 / 说明）
- 最小可运行示例

全部录入后删除文件顶部的「待填充」标记。

### 3. `SKILL.md` 检查命令配置

「检查命令配置」表中默认值为 `shell_check`。若实际命令不同（如 `shellcheck`、`pnpm check` 或内部检查工具），修改该表即可，例如：

```markdown
| 检查命令 | `shellcheck --severity=warning` | 静态检查，警告级及以上必须清零 |
```

## 已知边界（刻意留白）

- **无测试规范**：Step 4 仅内置 shell_check 静态检查门禁；单元/集成测试要求请填入 `reference/STANDARDS.md` 第 5 节（编码强制约定），需要独立测试技能时另行创建
- **无需求/方案设计能力**：上游交给 `solution-design`（深度）或 `dev-workflow`（轻量），本技能只负责编码阶段
- **术语/领域建模**：不在本技能范围，需要时另行自建独立技能
