# 规范驱动编码

需求分解 → 熟悉规范与公共库 → 代码实现 → shell_check 检查优化

两条铁律：

1. **规范即准绳，公共库优先**：实现必须符合 [STANDARDS.md](reference/STANDARDS.md)，公共库已有的能力禁止重复造轮子
2. **检查不过，不算完成**：shell_check 通过、且优化后复跑仍通过，才能声称完成

## 使用时机

- 用户要求按开发规范、公共库进行代码开发
- 用户给出需求，期望走「分解 → 熟悉规范 → 实现 → 检查优化」完整流程
- 用户提到「规范开发」「公共库」「shell_check」

## 任务进度

开始前复制此清单，逐步勾选：

```
任务进度：
- [ ] Step 1：需求分解
- [ ] Step 2：熟悉开发规范与公共库接口
- [ ] Step 3：用代码实现方案逻辑
- [ ] Step 4：调用 shell_check 检查并优化代码
```

## Step 1：需求分解

1. 通读需求，拆解为可独立实现、可独立验证的子任务
2. 每个子任务明确输入、输出、边界条件
3. 标注子任务间依赖，确定实现顺序
4. 输出《需求分解清单》：

| # | 子任务 | 输入 | 输出 | 依赖 |
|---|--------|------|------|------|
| 1 |        |      |      | —    |

> 需求有歧义时，先向用户澄清，再进入 Step 2。

## Step 2：熟悉开发规范与公共库接口

**未完成本步骤，不得编写实现代码。**

1. 通读 [STANDARDS.md](reference/STANDARDS.md)（开发规范）
2. 通读 [COMMON-LIBRARIES.md](reference/COMMON-LIBRARIES.md)（公共库接口）
3. 圈定本次开发涉及的规范条目与公共库接口，输出对照清单
4. 若任一文件仍含「待填充」标记（空模板）：
   - 停下提醒用户填充后再继续；或
   - 经用户确认后，按语言通用最佳实践代替规范继续，并在交付物中注明

## Step 3：用代码实现方案逻辑

1. 按 Step 1 确定的顺序逐一实现子任务
2. 动手前先查 Step 2 圈定的公共库接口：**已有能力必须复用，禁止重复造轮子**
3. 每完成一个子任务，立即对照规范条目自查（命名、结构、错误处理等）
4. 代码风格与目标代码库既有代码保持一致

## Step 4：调用 shell_check 后优化代码

反馈循环，直到全部通过：

1. 运行检查命令（默认 `shell_check`，见下方「检查命令配置」）
2. 逐条处理告警：真实问题 → 修复；误报 → 注明理由，不得静默忽略
3. 修复后重新运行，直到零告警
4. 通过后做一轮优化：消除重复、简化逻辑、删除死代码、把新沉淀的公共能力收敛进公共库
5. **优化后必须复跑检查**，确认仍全部通过

## 检查命令配置

| 配置项 | 当前值 | 说明 |
|--------|--------|------|
| 检查命令 | `shell_check` | 默认值；若实际命令是 `shellcheck` 或内部检查工具，修改此处即可 |

## 知识库（用户维护）

| 文件 | 内容 | 维护方式 |
|------|------|---------|
| [STANDARDS.md](reference/STANDARDS.md) | 开发规范：语言版本、命名约定、目录结构、错误处理等 | 用户填充，逐条替换「待填充」标记 |
| [COMMON-LIBRARIES.md](reference/COMMON-LIBRARIES.md) | 公共库接口：库名、引入方式、核心接口、使用示例 | 按文件内模板逐库添加 |

## 与其他技能的关系

- dev-workflow 的「需求理解 / 方案设计」产出可直接作为本技能 Step 1 的输入；本技能聚焦编码与检查优化阶段
- 检查通过后如需人工审查，衔接 dev-workflow 的「代码审查」步骤
